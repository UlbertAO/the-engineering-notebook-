# Git & GitHub for Beginners: Understanding Version Control and Essential Git Commands

Before diving into what Git and GitHub are, let's understand what a **Version Control System** is.

## Version Control System

A **Version Control System (VCS)** is a tool used to manage and track changes throughout a project's development lifecycle. It is also known as **source control** or **revision control**.

A VCS allows developers to track the entire history of changes made to a project and see who made them. If incompatible changes are introduced into the main codebase, previous versions can be restored when needed.

Version control systems also make collaboration possible. They can be **centralized**, where the tracked files and their history are stored on a central server, or **distributed**, where the repository can be cloned to multiple machines, each containing its own copy of the repository and its history.

Some well-known VCS tools are:

- Git
- Subversion
- Mercurial

## Git

Among these, **Git** is one of the most popular choices among developers. It is an **open-source distributed version control system**.

You can take a look at the [Git source code](https://github.com/git/git).

Git can be used through the command line, and several GUI clients are also available. I recommend learning Git through the command line because it gives you access to Git's full set of commands and provides more flexibility.

There are four states we commonly encounter when working with Git:

- **Untracked**: Files that are not being tracked by Git.
- **Unmodified**: Files that are being tracked by Git but have not been modified since the last commit.
- **Modified**: Files that are being tracked by Git and contain changes that have not yet been staged.
- **Staged**: Files whose changes have been added to the staging area and are ready to be committed.

During the development process, we may create a new file to write code in. Initially, this file is **untracked**. Once we have finished making changes, we can add those changes to the **staging area** and commit them so that we can return to an earlier version if something goes wrong.

After the commit, the file is considered **unmodified** because its contents match the latest commit. If a developer makes further changes to the file, Git marks it as **modified**, indicating that there are changes that can be staged and committed.

Each commit is recorded in the project's repository history.

## GitHub

A **repository** is a place that contains a project's files along with its version history.

**GitHub** is a platform where we can host Git repositories and collaborate with others.

Similar platforms that provide these kinds of services include:

- GitBucket
- Bitbucket
- GitLab

Public repositories on GitHub can be viewed by anyone. However, users need appropriate permissions to make direct changes to a repository.

Throughout this section, we'll use the following format for Git commands:

> `command [arguments]`

### Configuring Git

Once Git is installed, you can configure your author information either **locally** for a specific repository or **globally** for all repositories. This information is used to identify the author of your commits.

- Sets the name associated with your commits.

```
git config --global user.name "[name]"
```

- Sets the email address associated with your commits.

```
git config --global user.email "[email address]"
```

- Lists the current global Git configuration.

```
git config --global -l
```

There are many other Git configuration options that can be set as needed.

### Initializing a Repository

When starting a project that we want Git to track, we first initialize it as a Git repository.

Initializes a Git repository in the current directory.

> git init

You can also provide a directory name:

> git init [projectName]

Creates a new Git repository inside the specified directory.

### Staging Changes

During development, new files may be added and existing files may be modified. These changes can be added to the **staging area** before committing them.

```
git add [fileName]
```

Stages the specified file's changes.

To stage all changes in the current directory:

```
git add .
```

Stages new, modified, and deleted files in the current directory and its subdirectories.

If you have staged changes that you no longer want to include in the next commit, you can remove them from the staging area:

```
git restore --staged [fileName]
```

Removes the specified file's changes from the staging area while keeping the changes in the working directory.

### `.gitignore`

Sometimes we may want Git to ignore certain files, such as files generated by the development environment, build artifacts, or files containing local configuration.

Paths for these files can be added to a `.gitignore` file so that Git does not track those files.

For example:

```
node_modules/
.env
dist/
```

### Committing Changes

Once the desired changes have been staged, they can be recorded in the project's version history using a commit.

```
git commit -m "commit message"
```

Records the staged changes in the project's version history.

For example:

```
git commit -m "Add user authentication"
```

A good commit message should briefly describe the changes introduced by the commit.

### Resetting Commits

Git also provides the `reset` command for moving the current branch to a previous commit.

```
git reset [commitHash]
```

Moves the current branch to the specified commit and unstages changes from commits after it while keeping those changes in the working directory.

Git provides different reset modes, such as `--soft`, `--mixed`, and `--hard`, which behave differently. Be especially careful with `--hard` because it can discard local changes.

### Checking Repository Status

At any point, you can check the current state of your working directory and staging area:

```
git status
```

Shows the current state of files in the working directory and staging area.

### Viewing Commit History

To view the commit history of a repository:

```
git log
```

Displays the commit history of the repository.

### Cloning a Repository

If a repository already exists on a remote server such as GitHub, we can create a local copy of it using:

```
git clone [url]
```

Creates a local copy of a remote repository.

For example:

```
git clone https://github.com/example/project.git
```

## Branches

Branches are one of Git's most powerful features. They allow developers to work on changes independently without affecting the main branch until those changes are ready to be merged.

For example, a developer can create a separate branch to work on a new feature while the `main` branch remains stable.

### Creating a Branch

```
git branch [branchName]
```

Creates a new branch.

The `-d` option can be used to delete a branch:

```
git branch -d [branchName]
```

Deletes the specified branch.

### Switching Branches

Git provides the `switch` command specifically for working with branches:

```
git switch [branchName]
```

Switches to the specified branch.

A new branch can be created and checked out at the same time:

```
git switch -c [branchName]
```

Creates a new branch and switches to it.

You may also come across `git checkout` in older tutorials and existing projects. It can also be used to switch branches:

```
git checkout [branchName]
```

Switches to the specified branch.

### Merging Branches

Once the changes on a branch are ready, they can be merged into another branch.

```
git merge [branchName]
```

Merges the changes from the specified branch into the current branch.

For example, if you are currently on the `main` branch:

```
git merge feature-login
```

This merges the changes from `feature-login` into `main`.

## Git Stash

The **stash** is a place where changes can be stored temporarily without committing them to the repository.

It can be useful when we need to temporarily set aside our current changes and work on something else without committing them.

The stash works like a **stack**: each new stash is placed on top of the previous ones.

### Stashing Changes

```
git stash -m "stash message"
```

Saves the current changes to the stash and gives you a clean working directory.

The `-u` option can be used to include untracked files:

```
git stash -u
```

Stashes tracked and untracked files.

The `-a` option can be used to include all files, including ignored files:

```
git stash -a
```

### Restoring Stashed Changes

```
git stash pop
```

Applies the most recent stash and removes it from the stash list.

A specific stash can be restored using its stash identifier:

```
git stash pop stash@{n}
```

Applies the specified stash and removes it from the stash list.

## Working with Remote Repositories

A local Git repository and a repository hosted on GitHub can be synchronized with each other.

To do this, Git uses a **remote repository URL**. The `remote` command is used to manage these remote connections.

After creating a repository on GitHub and developing the project locally, we can connect the local repository to the remote repository and push our commits to GitHub.

### Adding a Remote Repository

```
git remote add origin [RepositoryURL]
```

— Adds a remote repository and gives it the name `origin`.

`origin` is the conventional name used for the default remote repository. Once the remote has been added, we can use `origin` instead of typing the complete repository URL every time.

For example:

```
git remote add origin https://github.com/example/project.git
```

### Fetching Changes

```
git fetch
```

Downloads commits and other updates from the remote repository without modifying your current working branch.

### Pulling Changes

```
git pull
```

Fetches changes from the remote repository and integrates them into the current branch.

In the common case, `git pull` can be thought of as a `git fetch` followed by a merge.

### Pushing Changes

```
git push
```

Uploads local commits to the remote repository.

For both `push` and `pull`, we can specify which remote and branch to use:

```
git push origin main
```

Pushes the local `main` branch to the `origin` remote.

```
git pull origin main
```

Fetches and integrates changes from the `main` branch of the `origin` remote.

The general syntax is:

```
git push [remote] [branch]
git pull [remote] [branch]
```

## Forking a Repository

**Forking** a repository means creating a copy of someone else's repository under your own GitHub account.

When contributing to a repository that you don't have write access to, you typically cannot push directly to it. A fork gives you your own copy where you can make and push changes.

Once the repository has been forked, we can make changes to our copy and push them to our GitHub repository.

When we want those changes to be included in the original repository, we can open a **Pull Request**. The maintainers can then review the changes and, if they approve them, merge them into the original codebase.

This workflow makes it possible for developers to contribute to open-source projects without requiring direct write access to the original repository.
